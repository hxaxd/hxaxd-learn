# 云智能体 (Cloud Agent)

- 单智能体只需要操心它做得好不好, 一旦把它放到云端服务很多人, 就要操心一串新问题: 怎么隔离, 怎么调度, 怎么不丢状态, 怎么伸缩, 怎么不出事故

## 架构

- 平台必须先区分管理配置的控制面和实际承载任务的数据面, 再选择部署载体
- 控制面: 版本, 策略, 身份, 调度这些配置变化较慢, 要与任务执行流量隔离开
- 数据面: 模型调用, 工具执行和状态读写在高频路径上, 需要独立伸缩和故障控制
- 部署: 控制面和数据面最终映射到具体计算形态, 部署方式决定了资源和运维边界
    - 容器编排 (Kubernetes): 要精细控制长任务, 网络和多租户资源时, 用它提供完整调度面
    - 无服务器 (Serverless): 短时或突发任务适合按需计费免运维, 但受时长和状态限制

## 执行

- 智能体不是一次函数调用, 一条任务要经过 排队 -> 分配 -> 运行 -> 结果传输 这条链
- 会话: 用户连续交互需要稳定身份和短期资源, 寿命通常跨越多个任务
- 任务: 云端可排队, 重试, 计费的最小执行单位
- 队列: 任务到达有突发性且执行时间长, 用它吸收负载并做优先级
- 工作节点: 实际执行落到受控计算节点, 承担资源配额和故障域
- 持久执行: 长任务不能依赖单个进程存活, 要保证步骤可续接
- 流式: 交互体验要在任务完成前就返回事件, 它与最终结果存储职责不同
- 后台执行: 不需要持续交互的任务释放前台连接, 但保留状态和通知路径
- 事件: 除了用户请求, 文件, 消息, 系统事件也能触发, 入口要统一接入执行链

## 沙箱

- 智能体会跑不可信代码并访问工作文件, 隔离环境是云端执行的基本资源单位
- 隔离强度, 启动速度和兼容性没法同时最优, 所以要在几种技术边界上取舍
    - 容器: 启动快生态全, 但共享内核, 隔离强度有限
    - 用户态内核沙箱 (gVisor): 在容器兼容性与更强的系统调用隔离之间折中
    - 微型虚拟机 (microVM): 用更强的内核边界换更高的启动和资源成本
    - 虚拟机 (VM): 提供最成熟的强隔离, 但密度和冷启动最差
    - 网页汇编 (Wasm): 受限运行时, 适合可移植小型计算, 系统接口和兼容性有限
- 镜像: 任务环境必须从可版本化的依赖基线创建, 否则执行不可复现
- 快照: 完整冷启动太贵时, 在隔离不变的前提下复用初始化状态
- 文件系统: 代码和产物需要持久读写, 但文件可见范围受租户和任务约束
- 网络: 工具常要联网而不该任意外连, 网络策略决定可达服务与数据出口
- 生命周期: 沙箱从创建到销毁经过初始化, 使用, 暂停, 回收, 每阶段资源语义不同
- 预热池: 按需创建赶不上低延迟峰值, 用闲置成本换启动速度
- 提供商: 隔离能力也可能来自外部平台, 要单独评估接口, 可移植性和信任边界
    - E2B: 一个把生命周期, 模板和持久化做成服务接口的例子, 也暴露了供应商依赖

## 网关

- 模型, 工具和智能体入口的协议与治理对象都不同, 不能用一个通用反向代理概括
- 智能体网关: 面向用户或客户端, 负责身份, 会话和任务路由, 治理对象是任务而不是单次模型调用
- 模型网关: 各模型供应商接口, 配额, 故障各异, 需要统一调用和成本治理
    - 协议: 供应商请求和事件格式不同, 统一之后上层才能切模型
    - 路由: 按能力, 区域, 配额选模型, 不能固定打一个后端
    - 负载均衡: 同模型的多个实例分摊请求, 兼顾缓存亲和与健康状态
    - 降级: 首选模型不可用或超额时受控降级, 但要清楚能力差异
    - 限流: 供应商和租户都有调用上限, 在进下游之前保护配额
    - 语义缓存: 语义等价请求能复用最终响应, 与模型内部前缀缓存的命中条件不同
    - 预算: 路由不只追质量, 还要给用户和任务约束累计成本
    - LiteLLM: 一个承载协议归一, 路由和成本治理的具体实现
- 工具网关: 工具连接带用户凭证和资源权限, 其注册和认证不能复用模型路由
    - MCP: 标准工具协议提供发现和调用契约, 是接入异构工具的共同接口
    - 注册表: 工具端点, 版本, 能力会变, 让路由和发现脱离硬编码
    - 身份认证: 先确认调用主体和工具服务身份, 才能建立信任
    - 凭证代理: 用户凭证在网关内按调用代取注入, 不暴露给模型或沙箱

## 状态

- 计算节点可以短暂存在, 但对话, 检查点和产物必须跨节点持续
- 对话: 承载用户交互连续性, 但不应与执行检查点混为一份记录
- 检查点: 恢复需要能重建执行位置的确定状态, 普通消息历史不足以续跑
- 记忆: 跨会话知识有独立寿命和访问策略, 不随计算节点销毁
- 产物: 中间和最终产物可能很大且要交付, 适合对象存储而非上下文数据库
- 工作区: 运行中的可变文件系统要能重新挂载或迁移, 一致性要求不同于产物

## 伸缩

- 智能体任务时长和扇出差异巨大, 传统请求并发不足以描述容量问题
- 并发: 同时运行的任务数直接决定模型, 工具, 沙箱占用, 是容量的第一约束
- 背压: 下游饱和还继续接任务会放大超时和重试, 压力要向上游传
- 自动伸缩: 负载变化要自动增减工作节点, 但长任务让缩容和预测更难
- 粘性路由: 会话缓存和本地工作区可能要求请求回同一节点, 会限制均衡自由度
- 扇出: 一个任务可能生成大量子任务或工具调用, 入口请求数代表不了真实负载
- 容量: CPU, 内存, 模型配额, 沙箱数量共同形成瓶颈, 需要统一容量模型
- 配额: 多租户共享资源必须设上限和优先级, 防单个用户占满系统
- 冷启动: 新沙箱和工作节点启动占交互延迟大头, 要单独测量和优化

## 可靠性

- 长任务跨越多个外部系统, 局部故障和重复执行是常态而不是例外
- 超时: 外部模型和工具可能永久等待, 每层调用都要有有限时间预算
- 重试: 瞬时故障能重做, 但重试会增加成本并可能重复副作用
- 幂等性: 任务被重复投递时要保持业务结果一致, 是安全重试的前提
- 去重: 即使操作幂等, 重复执行也浪费昂贵资源, 要在入口识别重复任务
- 熔断器: 下游持续失败还继续调用只会扩大拥塞, 熔断用于快速隔离故障
- 局部失败: 多步骤任务常有部分成功, 不能简单按整体失败全部重做
- 恢复: 节点或步骤失败后从检查点重新分配并继续, 是运行级恢复
- 灾难恢复: 区域或核心存储故障超出单任务范围, 要平台级备份和切换

## 安全

- 多租户平台同时处理代码, 凭证和外部数据, 需要纵深控制而非只靠沙箱
- 租户隔离: 不同用户的代码, 状态, 计算资源互不可见, 是多租户信任基础
- 智能体身份: 后台智能体不是用户本人, 要有可审计可限制的独立执行身份
- 授权: 身份只说明是谁, 授权才判断能对具体资源做什么
- 密钥: 工具访问依赖凭证但模型不应直接看到原文, 要受控注入
- 网络: 外连既是能力来源也是数据出口, 边界要按任务和租户实施
- 提示词注入: 云智能体会摄取大量不可信内容, 攻击能跨工具和会话传播
- 数据治理: 存储位置, 保留时间, 用途受组织和法规约束, 不只是访问权限
- 审计: 高权限自动操作必须留下不可抵赖记录, 才能查责任和合规
- 供应链: 镜像, 工具, 依赖都可能被污染, 运行时隔离替代不了来源治理

## 运维

- 上线后还要持续回答系统是否健康, 质量是否退化, 版本如何安全变更
- 可观测性: 把一次任务跨越的模型, 工具, 沙箱, 状态操作关联起来
    - 追踪: 端到端因果链连接各组件耗时和错误, 是长任务定位根因的主索引
    - 日志: 组件细节和异常上下文要可检索文本, 不能全塞成指标
    - 指标: 容量和健康要聚合统计, 支撑告警和自动伸缩
    - 采样: 全量保留高体积轨迹太贵, 采样决定可见性和开销的平衡
    - 成本: 模型, 沙箱, 工具费用来自不同系统, 要按任务和租户归因
- 评测: 系统健康不代表智能体质量稳, 运维还要持续看任务效果
    - 在线评测: 线上样本反映真实分布和系统交互, 发现离线数据没覆盖的问题
    - 漂移: 模型, 工具, 任务都会变, 质量基线可能在无代码变更时失效
- 注册表: 大量智能体和工具要有可发现的元数据入口, 否则版本依赖无法治理
- 版本: 提示词, 工具, 运行配置共同决定行为, 每个可部署组合都要身份
- 发布: 新版本不要一次覆盖全部流量, 渐进发布限制未知退化
- 回退: 质量或可靠性异常时要快速回到已知版本, 不能等修复
- 服务等级目标 (SLO): 延迟, 成功率, 质量要转成可运营承诺, 才能指导容量和告警
- 事故: 自动化系统仍会跨组件故障, 事故流程负责止损, 沟通和复盘

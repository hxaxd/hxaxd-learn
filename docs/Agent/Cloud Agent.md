# Cloud Agent

- 多租户托管和规模化运行

## 架构

- 平台必须区分管理配置的控制面和实际承载任务的数据面, 再选择部署载体
- Control Plane(控制面): 版本, 策略, 身份和调度配置变化较慢, 应与任务执行流量隔离
- Data Plane(数据面): 模型调用, 工具执行和状态读写位于高频路径, 需要独立伸缩和故障控制
- Deployment(部署): 控制面和数据面最终要映射到具体计算形态, 部署方式决定资源与运维边界
    - Kubernetes(容器编排平台): 需要精细控制长任务, 网络和多租户资源时, 容器编排提供完整调度面
    - Serverless(无服务器计算): 短时或突发任务更适合按需计费和免运维执行, 但受到时长和状态限制

## 执行

- 排队 -> 分配 -> 运行 -> 结果传输
- Session: 用户连续交互需要稳定身份和短期资源, 其寿命通常跨越多个任务
- Task: 任务是可排队, 重试和计费的云端执行单位
- Queue: 任务到达具有突发性且执行时间长, 队列用于吸收负载并实施优先级
- Worker: 实际执行必须落到受控计算节点, 工作节点承担资源配额和故障域
- Durable Execution: 长任务不能依赖单个进程存活, 持久执行保证步骤可续接
- Streaming: 交互体验需要在任务完成前返回事件, 流式通道与最终结果存储职责不同
- Background: 无需持续交互的任务应释放前台连接, 但仍保留状态和通知路径
- Event: 除用户请求外还存在文件, 消息和系统事件触发, 事件入口需要统一接入执行链

## 沙箱

- 智能体会运行不可信代码并访问工作文件, 隔离环境是云端执行的基本资源单位
- 隔离技术: 隔离强度, 启动速度和兼容性无法同时最优, 需要比较不同技术边界
    - Container(容器): 容器启动快且生态完整, 但共享内核使隔离强度有限
    - gVisor(用户态内核沙箱): 用户态内核在容器兼容性与更强系统调用隔离之间折中
    - MicroVM(微型虚拟机): 微型虚拟机用更强内核边界换取高于容器的启动和资源成本
    - VM(虚拟机): 完整虚拟机提供最成熟的强隔离, 但密度和冷启动最差
    - Wasm(网页汇编): 受限运行时适合可移植的小型计算, 但系统接口与软件兼容性有限
- Image(镜像): 任务环境必须从可版本化依赖基线创建, 否则执行不可复现
- Snapshot(快照): 完整冷启动成本过高时, 快照在隔离不变的前提下复用初始化状态
- Filesystem(文件系统): 代码和产物需要持久读写, 但文件可见范围必须受租户和任务约束
- Network(网络): 工具常需联网而不应任意外连, 网络策略决定可达服务和数据出口
- Lifecycle(生命周期): 沙箱从创建到销毁会经历初始化, 使用, 暂停和回收, 每阶段资源语义不同
- Warm Pool(预热池): 按需创建无法满足低延迟峰值, 预热池用闲置成本换启动速度
- Provider(提供商): 隔离能力可能来自外部平台, 需要单独评估接口, 可移植性和信任边界
    - E2B(云端沙箱平台): 外部沙箱平台展示生命周期, 模板和持久化如何以服务接口提供, 也暴露供应商依赖

## 网关

- 模型, 工具和智能体入口具有不同协议与治理对象, 不能由一个通用反向代理概括
- Agent Gateway(智能体网关): 面向用户或客户端的入口负责身份, 会话和任务路由, 对象不是单次模型调用
- Model Gateway(模型网关): 模型供应商接口, 配额和故障各异, 需要统一调用与成本治理
    - Protocol(协议): 供应商请求和事件格式不同, 统一协议才能让上层切换模型
    - Routing(路由): 模型选择取决于能力, 区域和配额, 不能固定发送到单一后端
    - Load Balancing(负载均衡): 同一模型的多个实例需要分摊请求, 同时兼顾缓存亲和和健康状态
    - Fallback(降级): 首选模型不可用或超额时需要受控降级, 但必须知道能力差异
    - Rate Limit(速率限制): 供应商和租户都有调用上限, 限流负责在进入下游前保护配额
    - Semantic Cache(语义缓存): 语义等价请求可复用最终响应, 这与模型内部前缀缓存的命中条件不同
    - Budget(预算): 路由不仅追求质量, 还要为用户和任务约束累计成本
    - LiteLLM(模型网关): 具体网关实现用于承载协议归一, 路由和成本治理的工程细节
- Tool Gateway(工具网关): 工具连接携带用户凭证和资源权限, 其注册与认证不能复用模型路由
    - MCP(模型上下文协议): 标准工具协议提供发现和调用契约, 是网关接入异构工具的共同接口
    - Registry(注册表): 工具端点, 版本和能力会变化, 注册表让路由与发现脱离硬编码
    - Authentication(身份认证): 网关必须先确认调用主体和工具服务身份, 才能建立信任
    - Credential Proxy(凭证代理): 用户凭证应在网关内按调用代取和注入, 避免暴露给模型或沙箱

## 状态

- 计算节点可以短暂存在, 但对话, 检查点和产物必须跨节点持续
- Conversation(对话): 对话历史承载用户交互连续性, 但不应与执行检查点混为一份记录
- Checkpoint(检查点): 恢复需要保存可重建执行位置的确定状态, 普通消息历史不足以续跑
- Memory(记忆): 跨会话知识需要独立寿命和访问策略, 不能随着计算节点销毁
- Artifact(产物): 最终和中间产物可能很大且需交付, 适合对象存储而非上下文数据库
- Workspace(工作区): 运行中的可变文件系统需要被重新挂载或迁移, 其一致性要求不同于产物

## 伸缩

- 智能体任务时长和扇出差异巨大, 传统请求并发不足以描述容量问题
- Concurrency(并发): 同时运行任务数直接决定模型, 工具和沙箱资源占用, 是容量的第一约束
- Backpressure(背压): 下游饱和时继续接收任务会放大超时和重试, 必须向入口传递压力
- Autoscaling(自动伸缩): 负载变化需要自动增减工作节点, 但长任务使缩容和预测更困难
- Sticky Routing(粘性路由): 会话缓存和本地工作区可能要求请求回到同一节点, 这会限制均衡自由度
- Fanout(扇出): 一个任务可能生成大量子任务或工具调用, 入口请求数无法代表真实负载
- Capacity(容量): CPU, 内存, 模型配额和沙箱数量共同形成瓶颈, 需要统一容量模型
- Quota(配额): 多租户共享资源必须设上限和优先级, 防止单个用户占满系统
- Cold Start(冷启动): 新沙箱和工作节点启动会占据交互延迟大头, 必须单独测量和优化

## 可靠性

- 长任务跨越多个外部系统, 局部故障和重复执行是常态而不是例外
- Timeout(超时): 外部模型和工具可能永久等待, 每层调用都需要有限时间预算
- Retry(重试): 瞬时故障可以重做, 但重试会增加成本并可能重复副作用
- Idempotency(幂等性): 任务被重复投递时必须保持业务结果一致, 这是安全重试的前提
- Deduplication(去重): 即使操作幂等, 重复执行仍会浪费昂贵资源, 需要在入口识别重复任务
- Circuit Breaker(熔断器): 下游持续失败时继续调用只会扩大拥塞, 熔断用于快速隔离故障
- Partial Failure(局部失败): 多步骤任务常有部分成功, 不能简单按整体失败全部重做
- Recovery(恢复): 节点或步骤失败后需要从检查点重新分配并继续, 这是运行级恢复
- Disaster Recovery(灾难恢复): 区域或核心存储故障超出单任务恢复范围, 需要平台级备份和切换

## 安全

- 多租户平台同时处理代码, 凭证和外部数据, 需要纵深控制而非只靠沙箱
- Tenant Isolation(租户隔离): 不同用户的代码, 状态和计算资源必须互不可见, 这是多租户信任基础
- Agent Identity(智能体身份): 后台智能体不是终端用户本人, 需要可审计且可限制的独立执行身份
- Authorization(授权): 身份只说明是谁, 授权还要判断其能对具体资源执行什么动作
- Secrets(密钥): 工具访问依赖凭证但模型不应直接看到原始密钥, 需要受控注入
- Network(网络): 外连既是能力来源也是数据出口, 网络边界必须按任务和租户实施
- Prompt Injection(提示词注入): 云端智能体会摄取大量不可信内容, 攻击可跨工具和会话传播
- Data Governance(数据治理): 数据存储位置, 保留时间和用途受到组织与法规约束, 不只是访问权限问题
- Audit(审计): 高权限自动操作必须留下不可抵赖记录, 才能调查责任和合规性
- Supply Chain(供应链): 镜像, 工具和依赖都可能被污染, 执行时隔离无法替代来源治理

## 运维

- 上线后还要持续回答系统是否健康, 质量是否退化以及版本如何安全变更
- Observability(可观测性): 平台需要把一次任务跨越的模型, 工具, 沙箱和状态操作关联起来
    - Trace(追踪): 端到端因果链连接各组件耗时和错误, 是长任务定位根因的主索引
    - Log(日志): 组件细节和异常上下文需要可检索文本, 无法全部压缩为指标
    - Metric(指标): 容量和健康状态需要聚合统计, 才能支持告警与自动伸缩
    - Sampling(采样): 全量保留高体积轨迹成本过高, 采样决定可见性与开销的平衡
    - Cost(成本): 模型, 沙箱和工具费用来自不同系统, 必须按任务和租户统一归因
- Evaluation(评测): 系统健康不代表智能体质量稳定, 运维还需持续观察任务效果
    - Online(在线评测): 线上样本反映真实分布和系统交互, 用于发现离线数据未覆盖的问题
    - Drift(漂移): 模型, 工具和用户任务都会变化, 质量基线可能在无代码变更时失效
- Registry(注册表): 大量智能体和工具需要可发现的元数据入口, 否则版本与依赖无法治理
- Version(版本): 提示词, 工具和运行配置共同决定行为, 每个可部署组合都需要身份
- Rollout(发布): 新版本不应一次覆盖全部流量, 渐进发布用于限制未知退化影响
- Rollback(回退): 质量或可靠性异常出现时必须快速回到已知版本, 不能等待重新修复
- SLO(服务等级目标): 延迟, 成功率和质量目标需要转成可运营承诺, 才能指导容量与告警
- Incident(事故): 自动化系统仍会发生跨组件故障, 事故流程负责止损, 沟通和复盘

# Context

- 包括系统提示词 + 工具定义 + 用户消息 + 模型回复 + 工具执行结果

## Knowledge

- Knowledge 是 Context 中关于环境和任务的信息
    - Knowledge 表示提供给模型的信息, 不代表其一定客观为真, 其中可以包括事实, 观察, 假设, 预测和相互冲突的信息
- 对象标识 + 对象关系 + 状态 + 时间 + 版本 + 来源
    - 相同字段名不代表相同业务含义, 例如已完成与已支付
    - 保留会改变下一步判断的差别, 粒度随任务变化
- 原始资料是依据, 索引与摘要提供取回路径
- Belief 是基于当前信息形成的判断, 需要区分事实 / 假设 / 冲突 / 未知

## Objective

- Objective 是一种特殊的 Knowledge, 描述对环境状态, 行动轨迹或最终结果的偏好
    - 包括希望达到的 Goal, 不可违反的 Constraint 和判断完成的 Completion Criteria
    - 模型倾向于服从 Objective, 并围绕 Objective 进行推理与规划
- 多个来源的指令可能冲突, 必须先定义谁能覆盖谁
- 同一条指令不应在所有任务中永久生效, 必须明确其作用边界
    - workflow / skill / rules 都是在调控指令注入时间

## Observation 与 Feedback

- Observation 是 Runtime 从环境中取得并提供给模型的 Knowledge
    - Observation 描述环境中发生了什么, 但不直接表示结果相对于 Objective 是否正确
    - 模型对 Observation 的解释属于 Reasoning, 不等于 Observation 本身
- Feedback 是 Evaluation 产生并提供给模型的 Knowledge, 用于修正后续推理与行动
    - Feedback 可以来自环境, 测试, 人类, Critic 或模型自身, 不一定由 Action 直接返回
    - 模型倾向于高估 Observation 与 Feedback 的可信度, 因此需要保留其来源与可验证性
- 观察描述发生了什么, 反馈判断这件事是否符合目标, 两者会以不同方式更新后续行为
- 模型应该以此判断目标是否完成
- Agent 状态栏在上下文末尾注入动态的元信息
    - 注意力倾斜非常明显且几乎完全相信

## Cognitive Control

- Cognitive Control 是 Context 中关于如何处理 Knowledge 的模式
    - 直接影响模型的关注点, 抽象层级, 推理方向和行动倾向
    - 可以理解为激活模型已有行为模式的 index + 引导模型的注意分配与生成倾向
    - 主要形式是提示词注入
    - Workflow 是一种注入 Cognitive Control 的机制, 决定当前使用哪种 Cognitive Control

- 相同知识和目标仍可能产生不同策略

### 提示词

- 语气与风格
- 尽量结构化 -> MD / XML
- 按流程讲述并细化

### Reasoning

- 推理负责从已有信息产生判断, 是认知控制中处理当前不确定性的部分
- Reasoning 是模型对 Knowledge 的变换, 以产生判断, 预测, 解释或行动依据
    - Reasoning 通常降低与 Objective 相关的不确定性
    - 探索阶段也可能通过生成假设主动增加候选解释
- 亦称推理时计算

### Planning

- 规划负责把目标展开为未来动作, 解决的是跨步骤组织
- Planning 是根据 Objective, 当前 Belief 与 Action 的可能后果组织未来行动

### Workflow

- 工作流把推理和规划放入可重复的阶段结构, 使控制模式能够被稳定调用
- Workflow 决定使用 Cognitive Control 的流程
- 也包括对 Context 的直接操作
- 单次调用 -> Workflow (安全稳定) -> Agent (变通)

#### ReAct

- 思考-行动-思考-结束
- agent 决定下一步是行动还是结束

#### Reflection

- 引导模型回顾之前的行动和结果

#### Plan and Execute

- 长任务需要把全局组织与局部执行分开, 否则计划容易被即时观察淹没
- 先计划, 后执行, 计划阶段生成一个完整的计划, 执行阶段按照计划执行, 适用于需要多个步骤才能完成的任务
- 在执行中可能会遇到计划中没有考虑到的情况, 需要动态调整计划 (replanning)

#### Search

- 拓展 - 打分 - 过滤
- 树形推理

#### Claude Code

- Think: 理解意图, 制定计划
- Act: 选择工具并执行
- Observe: 检查结果与状态
- Repeat: 决定下一步继续 (以及如何继续) 或结束

## Context Management

### 选择

- 当前窗口不是整个工作世界
    - 常驻目标 / 约束 / 必须持续关注的决定
    - 文档 / 日志 / 历史轨迹按需取回
- 预先检索与 Agent 主动探索可以组合, 取舍包括延迟与资料新鲜度

- 进入上下文之前先决定信息价值, 才能避免低价值内容占用注意力

### 压缩

- 上下文压缩通过删除冗余的 Knowledge 来提高有效信号密度
- 将经历整理成可接续的工作状态
    - 已确认事实与约束
    - 当前产物与修改状态
    - 未决判断, 当前假设与缺少的证据
    - 排除过的解释与适用条件
    - 原始资料入口与下一步依赖
- 假设不能在摘要中变成事实, 外部材料不能在摘要中变成用户指令
- 不能重新取回的关键信息必须保留, 否则压缩会真的丢失证据
- 验证压缩: 让后续执行只依据接续状态继续, 检查最终任务能否完成
- 长上下文解决同时比较多少信息, 接续解决工作持续多久

- 本质是将思维链路 -> 知识
    - 还能缓解上下文焦虑
- 卸载 / 噪音删除 / 驻轮摘要都算
- 探索阶段的错误路径会被直接删除压缩
- 文件的旧版本会删除
- 把阶段性流程折叠
- 按固定结构输出压缩 + 最近对话 + 重要信息

### 卸载

- 有些信息不能删除但也不必常驻, 外置并保留取回路径形成独立机制
- 拦截 Bash 中那些不 AI-Native 的输出, 直接压缩为一个结构化的结果, 从而提高相关信息的覆盖率
    - 智能过滤: 去除噪音
    - 分组: 聚合相似项
    - 截断: 保留相关上下文, 删除冗余
    - 去重: 合并重复日志行并计数

### Branch

- 互斥假设若共享一份上下文会相互污染, 分支用于隔离探索路径
- 隔离优于压缩 (sub-agent)

## Action

- Action 是模型输出中可被 Runtime 解释为环境交互的部分
    - Action 的类型, 参数及可能后果会作为 Knowledge 提供给模型
    - 模型倾向于将渴望得到的知识或环境状态转换为 Action, 以满足 Objective 的要求
    - 环境状态对于模型来说不可直接观察, 只能由 Runtime 转换为 Observation 后进入 Context

### Schema

- 一个工具包括
    - name
    - description
    - parameters: JSON Schema 定义参数结构和类型
    - output_schema: JSON Schema 定义输出结构和类型
- 工具定义中强调使用边界 + 示例 + 性能 + 工具间协作
    - 无论如何, 请不要进行隐式设计

### 发现

- 先提供名称 / 适用条件 / 入口, 选中后再展开定义与材料
- 可用动作会随环境和权限变化, 模型不能假设工具集合恒定
- 例如 search_tools
- 渐进式披露, 按需加载工具

### 返回与验证

- 工具返回应保留对象, 状态, 时间与必要的下一步查询入口
- 动作回执 / 状态观察 / 最终验收分开
    - 请求被接受不能证明任务已经完成
    - 结果未返回不能证明动作没有发生

## 持续职责

- 一次任务结束与一个角色结束不同
- 职责 + 未解除的承诺 + 等待条件 + 变化中的现场
- 记忆保存谁在等谁, 什么变化需要恢复, 哪项决定已经失效
- 事件给出重新观察的机会, 不代表必须重新开工
- 等待 / 恢复 / 取消也属于工作状态

# Runtime(运行时)

- 成本控制与错误处理
- 运行时把模型输出变成可恢复且受控的环境变化, 因而必须分别处理循环, 状态, 调度, 工具, 协议, 扩展, 安全, 观测和评测

- Runtime 是 Action 与环境状态转变的接口, 也负责将环境状态转换为 Observation
- Runtime 可以承载调用, 调度, 重试和状态持久化等确定性机制, 但这里只关注其中会影响 Agent 智能表现的部分

## 循环

- 智能体不是一次函数调用, 必须说明每轮如何推进以及何时停止或继续

### Turn(对话轮次)

- 一次模型输入和输出是循环中最小可提交单位, 其他控制都围绕轮次边界发生

### 终止

- 模型可能持续产生动作, 必须有独立条件判断目标完成, 失败或资源耗尽

### 恢复

- 中断不应迫使长任务从头开始, 恢复需要重新建立状态和继续位置

## 状态

- 长程执行需要把不同寿命和所有权的数据分开, 否则无法持久化和恢复

### Run(运行实例)

- 一次完整执行需要最外层身份串联资源, 事件和最终结果

### Session(会话)

- 多个轮次共享短期连续性, 但会话寿命不一定等于一个任务

### Task(任务)

- 任务是可排队, 可交付和可失败的工作单位, 不能由会话边界代替

### Plan(计划)

- 计划是会随观察更新的意图状态, 与已经发生的执行事实不同

- 简易版直接存内存 + 每次全量更新
- 复杂版: 落盘 + 依赖图 + 并发 + 多接口 -> 多智能体

### Checkpoint(检查点)

- 仅保存当前值不足以恢复, 还需要能重建一致执行点的快照

- 隐形 git repo
- 在运行中写结构化的 checkpoint 文件, 以便检查历史记忆

### Artifact(产物)

- 任务产物要跨越运行生命周期交付给人或其他任务, 因此不能只留在上下文

### Workspace(工作区)

- 工具操作依赖可变的工作现场, 它与只读产物和模型上下文具有不同生命周期

## 调度

- 任务何时运行和以什么顺序运行不应交给模型临场决定, 需要确定性控制层

### Queue(队列)

- 输入速度与执行能力通常不匹配, 队列负责吸收压力并保存顺序

- 中途插入的消息需要等待模型空闲时插入
    - 多智能体
    - 后台任务
    - 人类引导

### Concurrency(并发)

- 并行可以提高吞吐但会引入资源竞争和状态冲突, 必须单独控制

### Background(后台执行)

- 长任务不应绑定一次前台请求, 后台执行负责解耦两者生命周期

### Timer(定时器)

- 有些任务由时间而非用户消息触发, 需要确定性的时间源

- 就是 corn

### Retry(重试)

- 瞬时失败可以重做但业务失败不应盲目重复, 重试需要独立策略

### Timeout(超时)

- 外部调用可能永久悬挂, 超时为资源占用和等待时间建立上界

### Cancel 与 Resume(取消与恢复)

- 用户需要在不丢弃全部进度的前提下夺回控制权, 取消与恢复因此成对出现

## 工具

- 不同工具改变环境的方式和风险不同, 运行时必须为执行提供统一边界

### Execution(执行)

- 所有工具都需要共同的调用, 超时, 返回和审计外壳, 这层不能由具体工具重复实现

### Shell(命令行外壳)

- 文本命令覆盖面广且开销低, 但其自由度和破坏性也需要独立边界

### Browser(浏览器)

- 网页操作依赖页面结构, 导航和网络状态, 与普通命令执行不同

### Computer Use(计算机操作)

- 像素和输入事件缺少稳定语义接口, 因而需要单独处理定位和回放

### Code Interpreter(代码解释器)

- 动态代码提供通用计算能力, 同时要求隔离依赖, 文件和执行资源

## 协议

- 客户端, 模型和工具来自不同实现, 互操作不能依赖某个产品的私有调用

### MCP(模型上下文协议)

- 模型到工具的连接需要统一能力发现和调用契约, 才能跨工具提供商复用

### ACP(智能体客户端协议)

- 编辑器与编码智能体之间还涉及会话, 文件和进度交互, 不能由工具协议代替

- 接入 IDE 的

### AG-UI(智能体用户交互协议)

- 用户界面需要消费流式状态和人机事件, 其数据模型不同于模型或工具调用

## 扩展

- 许多控制逻辑不应塞入提示词, 需要在运行路径上提供确定性扩展点

### Hooks(钩子)

- 生命周期固定位置的前后置控制需要低成本且可预测的回调

- 通过在 Agent 执行流程的不同阶段插入 Hooks 来实现对 Agent 行为的控制和调整
- 常见的 Hooks 包括:
    - 上下文压缩后: 可以在上下文被压缩后进行检查, 确保没有重要信息被误删
    - Auto 模式分类器拒绝操作后: 可以在 Auto 模式下检测到潜在的危险操作时进行干预
    - turn 结束: 可以在每个 turn 结束时进行总结和调整
    - 需要人类授权: 可以在需要人类授权的操作前进行提醒和等待授权
    - 调用工具前后: 可以在调用工具前后进行检查和处理, 确保工具调用的正确性和安全性

### Middleware(中间件)

- 跨越多个阶段的认证, 日志和策略需要组合式包裹执行链

### Plugins(插件)

- 扩展若要安装, 版本化和分发, 还需要高于单个回调的封装单位

## 安全

- 模型输出具有概率性且环境包含敏感资源, 行动能力必须受到独立约束

### Guardrails(护栏)

- 内容层风险需要依据输入和输出语义判断, 不能只靠资源权限

#### 输入

- 风险可能在模型行动前已经进入上下文, 因而需要入口检查

#### 输出

- 安全输入仍可能生成危险动作或内容, 因而需要出口检查

- 拒绝什么
    - 范围升级: 过度理解用户输入
    - 凭证探索: 自行探索系统中的敏感信息
    - 绕过安全检查: sudo 这一块
    - 数据外泄: 逗死我了这一块

### Permissions(权限控制)

- 即使意图安全, 动作仍只能访问被明确授权的资源

- 对 agent 的操作进行粗细粒度的权限控制, 粗判断可能危险才会细判断
    - YOLO: 一个 ML 驱动的分类器, 把风险分为低中高
- 对工具调用进行核验
    - 是否有权限访问资源
    - 是否是安全行为

### Approval(批准)

- 某些高影响动作需要把最终决定权交还人类, 自动权限不能覆盖这一边界

### Sandbox(沙箱)

- 权限判断可能出错, 沙箱通过环境隔离限制最坏后果

- 可以用沙箱以隔离环境并避免对系统造成损害
- 限制文件访问
- 限制网络访问

### Prompt Injection(提示词注入)

- 外部内容可能伪装成指令改变目标, 这种攻击发生在认知入口而非普通权限层

- Prompt Injection 扫描读取的所有内容, 如果内容在试图劫持 Agent, 探测器会在内容之前附加一条警告

### Data Exfiltration(数据外泄)

- 读取合法不代表可以对外发送, 数据出口必须独立于访问权限控制

## 可观测性

- 没有运行证据就无法定位失败或比较版本, 因而执行过程必须可追踪

### Trace(追踪)

- 一次任务跨越多轮和多工具, 只有因果链能还原端到端路径

### Log(日志)

- 离散事件和错误细节不适合全部聚合为指标, 需要保留可检索记录

### Metric(指标)

- 大规模运行无法逐条阅读日志, 指标用于发现总体趋势和异常

### Replay(回放)

- 调试概率性行为需要重现当时输入和状态, 单纯查看结果不足以定位根因

## Evaluation(评测)

- 可观测数据只说明发生了什么, 评测还要判断结果和过程是否足够好

### Online(在线评测)

- 在线评测能立即改变当前行为, 但会增加运行成本和反馈偏差

- 在线 Evaluation 发生在 Agent 的认知循环中
    - 依据 Objective 判断当前状态, Action 或结果
    - 将评价结果作为 Feedback 返回 Context
    - Feedback 会影响 Agent 后续的 Belief, Plan 和 Action
- Evaluation 与 Observation 不同
    - Observation 描述环境中发生了什么
    - Evaluation 判断发生的事情相对于 Objective 是否正确
- 在线评测
    - 安全全跑 (遥测)
    - 质量少跑一点

### Offline(离线评测)

- 离线评测提供可重复的版本比较, 不承担实时纠错

- Harness Evaluation 用于判断 Harness 中的 Knowledge, Cognitive Control 与 Runtime 是否有效
- Evaluation 的结果可以为 Evolution 提供修改 Harness 的依据
- cicd

### Outcome(结果)

- 最终结果直接对应任务价值, 但无法解释智能体是如何到达结果的

### Trajectory(轨迹)

- 过程质量能发现碰巧成功和危险捷径, 因而必须与结果分开

### Evaluator(评估器)

- 规则, 模型和人类评判的偏差不同, 评估来源本身需要建模

### Dataset(数据集)

- 没有覆盖真实任务分布的案例集, 指标无法代表上线表现

- 去掉目的工具, 看会不会拒绝
- 类似名字的工具, 看会不会搞混
- Prompt 里指定工具, 但可能夸大工具能力 / 工具不存在

### Metrics(指标体系)

- 评测结果需要统一口径才能跨版本, 场景和成本进行比较

#### 完成率

- 智能体首先要实际完成目标, 这是其他质量指标成立的前提

#### 幻觉率

- 结果可能形式正确却依赖虚构事实或工具, 需要独立衡量真实性

- 绝不解释增加
- 未知工具
- 影子工具
- 参数幻觉

#### 工具调用准确率

- 工具选择和参数错误是智能体特有失效源, 不能被最终成功率完全暴露

#### 错误恢复率

- 长程任务不可避免遇到失败, 能否恢复比是否零错误更能反映鲁棒性

#### 成本

- 相同质量可能消耗完全不同的调用和工具资源, 上线决策必须纳入效率

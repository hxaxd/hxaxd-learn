# Runtime

- Runtime 是 Action 与环境状态转变的接口, 也负责将环境状态转换为 Observation
- Runtime 可以承载调用, 调度, 重试和状态持久化等确定性机制, 但这里只关注其中会影响 Agent 智能表现的部分

## 执行与状态

### Turn

- 任务身份独立于一次模型调用 / 前台连接 / 工作进程
- 任务状态: 待执行 / 执行中 / 等待 / 完成 / 失败 / 取消
- 当前目标, 决定, 产物与执行记录需要能对应到同一项任务

- 一次模型输入和输出是循环中最小可提交单位, 其他控制都围绕轮次边界发生

### Plan

- 简易版直接存内存 + 每次全量更新
- 复杂版: 落盘 + 依赖图 + 并发 + 多接口 -> 多智能体

### Checkpoint

- 接续上下文 + 文件版本 + 依赖配置 + 服务状态 + 工具执行记录
- 恢复时重新确认真实状态, 本地回滚不撤销远端已经发生的动作
- 外部调用结果不明 -> 查询 / 对账 -> 确认后再重试
- 幂等标识需要由执行方落实, 相同标识不能悄悄代表不同请求
- 共享状态写入时核验版本, 防止旧观察覆盖新变化

- 隐形 git repo
- 在运行中写结构化的 checkpoint 文件, 以便检查历史记忆

## 调度与资源

### 队列

- 中途插入的消息需要等待模型空闲时插入
    - 多智能体
    - 后台任务
    - 人类引导

### Background

- 等待对象与恢复条件显式保存, 不需要模型空转等待
- 用户补充 / 工具返回 / 其他成员消息 / 取消需要按顺序进入任务记录
- 取消需要停止动作派发, 处理运行中的进程并回收资源
- 时间 / 轮次 / 费用 / 并发预算, 重试与子任务也计入
- 临时进程 / 文件 / 服务 / 浏览器都要有归属与清理方式

- 长任务不应绑定一次前台请求, 后台执行负责解耦两者生命周期

- 就是 cron

## 安全

- 执行层与数据层的防护更稳定重要
    - 尤其执行层中的输出层
- 超过失败阈值 / 高风险 -> Human in the Loop

### 输入

- Prompt Injection 扫描读取的所有内容, 如果内容在试图劫持 Agent, 探测器会在内容之前附加一条警告
- 上下文层
    - 打上来源标记 + 限制外部信息的角色
    - 相关性分类器拦截无关输入
    - 安全分类器拦截危险输入
    - 实现方法为内容审计与基于规则的保护
- Anthropic 的 Constitutional Classifiers5
    - 用自然语言写成的规则生成合成训练数据, 训练输入输出分类器
    - 上下文联合判断, 把用户提问和模型回答放在一起检查
    - 两级筛查, 先用轻量探针检查所有对话发现可疑之处再交给更强的分类器复审

### 输出

- 拒绝什么
    - 范围升级: 过度理解用户输入
    - 凭证探索: 自行探索系统中的敏感信息
    - 绕过安全检查: sudo 这一块
    - 数据外泄: 逗死我了这一块

### Permissions

- 隔离: 碰得到什么; 授权: 这次允许做什么
- 用户 + 任务 + 动作 + 目标资源 + 有效期
- 执行时再检查授权, 用户撤销后不能沿旧授权继续
- 可读取不等于可外发, 凭据可由受控服务代用

- 对 agent 的操作进行粗细粒度的权限控制, 粗判断可能危险才会细判断
    - YOLO: 一个 ML 驱动的分类器, 把风险分为低中高
- 对工具调用进行核验
    - 是否有权限访问资源
    - 是否是安全行为
- 数据出口必须独立于访问权限控制

### Sandbox

- 可以用沙箱以隔离环境并避免对系统造成损害
- 限制文件访问
- 限制网络访问

## 可观测性与评估

### 可观测性

#### Trace

- 任务原始要求 + 实际输入上下文 + 动作 + 返回 + 时间 + 环境状态 + 产物版本
- 产物 / 验证结果 / 修改理由必须关联到实际版本
- 保存操作证据不等于暴露模型内部完整推理

- OTEL 已经有 Agent 语义

#### Replay

- 调试概率性行为需要重现当时输入和状态

### Evaluation

- 可观测性 + 内部评估基础设施 + 仿真
- 验证方式
    - 确定性
    - 检查项
    - 评分标准 + LLM
    - 配对比较 (小心位置偏差)
- 结果的运用: 统计显著性 -> 失败归因 -> 回归任务 -> 迭代优化

#### 在线评测

- 人类偏好
- 监控高敏感指标, 遥测

#### 离线评测

- 任务来源
    - 公开基准 (benchmark)
    - 自建业务集
    - 生产轨迹回流
- 边界集 + 保留集

##### 环境

- Benchmark = 任务 + 环境 + 工具 + 验证器
- 固定环境版本, 初始状态与可控随机性, 其余波动通过重复运行观察
- 工具必须覆盖完成任务所需的观察与行动, 设施缺失不能直接归因模型
- 开发 / 候选选择 / 训练材料与独立测试隔离

- 数据集
- 环境状态
- 工具接口
- 评分标准
- 执行协议

##### 任务设计

- 用 Agent 模拟人类用户的行为
    - 约束用户认知边界 -> 装傻
    - 防止合家欢
    - 双边信息不透明
    - 最后校验结果

##### 设计

- Rubric 是标准, Judge 是执行者, 判断可以是标量 / 向量 / 结构化结果
- 一致不等于正确, 重复评判之外还需要专家对照与反例
- 修改评分标准与修改 Agent 分别验证, 尺子变了不能算能力变强
- 检查实际产物与环境结果, 不只检查最后一句回答

- 验证器很重要, 但只能根据任务定制
    - 成功条件要精确
- 难度分层
- 防范数据泄露 -> 无关信息混淆 + 金丝雀标识符
- 评分标准的设计
    - 基于专家指导
    - 全面覆盖
    - 按重要性加权
    - 评价标准客观可验证
- 古德哈特定律 -> 当指标成为目标时, 它就不再是一个好的指标
    - 多源异构评判

##### 失败归因

- 第一处导致结果走偏的错误, 不一定是第一处不顺利的探索
- 回到当时能看见的信息与真实状态, 区分知识 / 上下文 / 方法 / 工具 / 设施 / 标准
- 端到端回归检验原任务, 正确前缀继续评测检验目标判断
    - 前缀中的文字与环境状态必须对应, 停在目标决定之前
    - 整任务通过 / 局部失败 -> 可能绕过旧问题
    - 整任务失败 / 局部通过 -> 沿新轨迹检查其他原因
- 归因 -> 可修改对象 + 原始证据 + 假设 + 验证方式

- 拿到轨迹进行归因
    - 归因第一个错误
- 转换为端到端回归任务 + 轨迹前缀回归任务

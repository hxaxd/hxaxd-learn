# Human

## 意图

- 先明确交付物 / 使用者 / 完成证据, 形式与步骤服务于目标
- 尚未决定的结果取舍需要澄清, 已有事实由 Agent 自己调查
- 目标与约束可以稳定, 实现路径根据证据调整

- Goal: 目标状态
- Constraint: 不可接受的状态或行为
- Completion Criteria: 判断目标已完成所需的证据

### Spec 表达目标状态

- openspec
- spec-kit
- 没用的, 自然语言不可能收敛

## 交互

- 一次集中解决一个未决问题, 提供证据 / 可选结果 / 建议
- 中途纠正更新当前正确状态, 影响已有依赖时带回相关决定
- 进度说明保留已完成 / 等待对象 / 未决事项 / 下一步条件
- 人介入时应看到具体需要决定什么, 已确认的实现细节不必反复批准

- 缺乏在长任务当中不断的显示进度与状态, 使人类进行引导澄清
- 模型主动提问意愿不高

## 反馈

- 用户接受不自动证明正确, 拒绝也可能来自需求变化
- 保存反馈发生的情境, 区分缺陷 / 新要求 / 偏好 / 使用效果
- 当前结果修正与未来方法更新分别落实
- 判断来自人类也需要依据, 有争议时调查后再采纳

- 缺乏反馈转化机制 -> 重新做 / 记住

## 方法与案例

### superpowers skills

#### 原理

- 用 SPEC 交代意图
- 主动要求澄清 / 批准
- 零上下文计划
- 自动对抗式审查

#### 流程

- 入口 -> 定义基本约束 + 流程
- 头脑风暴 -> 架构
    - 目标, 约束, 成功标准
    - 通过提问一次澄清一个细节
- 计划 -> 零上下文工程师可执行的任务分解
    - 不要重复
    - 不做多余的工作
    - TDD
- TDD
    - 红: 失败的测试用例
    - 绿: 通过测试用例
    - 重构: 优化代码, 不改变功能
- 执行
    - 自主设定 checkpoint, 要求人类审查
- ReView
    - 左移: 尽可能早地发现问题
    - 细粒度: 每个最小化 Task 都需要 Review
    - 必须提供完整上下文
    - SOLID 原则
- 收到 ReView 反馈后
    - 不能因为配合而全盘接受 ReView 结果 (例如过度设计 / 删除向后兼容)
    - 先验证后执行
    - 敢于反驳
    - 与 ReView 人员完全澄清, 而不是部分接受
- DeBug
    - 根因调查 -> 模式分析 -> 假设验证 -> 修复
    - 三次失败直接放弃, 质疑架构问题

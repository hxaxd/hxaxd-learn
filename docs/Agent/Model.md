# Model

- 模型即 Agent -> Harness 的能力随轨迹内化进模型 (苦涩的教训)

## 能力

### 世界知识与语义理解

- 大规模预训练

### Instruction Following

- Harness 依靠指令激活行为, 指令遵循是其他智能体能力可控的前提
- 包括风格调整

### Reasoning

- 复杂任务需要在行动前组合证据和推导后果
- 推理时计算

### Tool Use

- 把意图转换为结构化外部动作
- 包括计算机操作

### Structured Output

- 下游系统需要机器可解析结果, 仅靠自然语言约定无法形成稳定接口
- 结构化输出依赖约束解码

### Long Context

- 可同时处理的信息规模直接限制长任务的连续性和证据覆盖
- 注意力分配中发现的模式
    - 模型会把多余注意力给序列的第一个 Token
    - 首尾上下文更容易被注意
    - 思考时频繁回看之前的内容
    - 输出时频繁回看思考的内容

### Multimodal

- 环境信息不只存在于文本, 图像和音频需要不同的感知能力

### 推理深度

- 对特定上下文的反应 `Reasoning: Low`

## 能力与支持条件

- 模型 / 上下文 / 工具 / 环境 / 预算共同决定一次系统表现
- 提示词改变本次计算条件, 不直接更新权重
- 行动底座包括工具使用 / 纠错 / 接续 / 接受中途指导
- 能力迁移到新领域仍需领域知识, 可执行环境与有效反馈
- 更强模型可能减少补偿流程, 是否能删要在任务中比较

## API 协议与服务

- 最早是聊天补全接口, 给个消息, 返回个消息
- Chat Template 负责序列化上下文

### Response API

- 消息是结构化的, 会被序列化为文本
    - system: 可以打点限制稳定前缀
    - user
    - assistant
    - tool_result
    - tool
    - 推理
    - ... 其实你在对话中看见的框框大抵对应一种对象
- 大部分情况我们都是追加内容
    - 指定 previous_response_id 并追加
    - 亦可分支

### 工具调用

- API 直接返回工具调用, 而不是文本
    - 帮你校验结构, 但是语义不一定
    - 工具调用与结果返回都是结构化的, 靠 id 对应
- 为了实现缓存
    - 工具列表尽量不变
    - 启动工具每次声明并注入
- 云端工具与本地工具
    - 云端自动继续循环
    - 云端工具不一定会把结果立刻给你, 可能会异步返回

### 流式输出

- 不仅流式输出文本, 同时流式输出结构化事件, 表达此时的状态
- SSE 或者 WebSocket

### 压缩

- API 直接提供上下文压缩
    - 可以设定触发时上下文大小
    - 禁止工具调用
    - 保留一部分上下文, 一部分做摘要
    - 摘要作为一个对象, 可见但不可查看内容
    - 可以提供指令

### 参数

- 主要控制选词空间 / 输出数量 / 思考强度
- 温度: 控制随机性
- 最大输出 token
- 推理深度: 注入提示词
- 结构化输出: 提示词设计 + 限制选词空间 + 后校验 / 处理

### Cache

- KV-Cache 特指一次推理中模型内部的注意力缓存, 由推理服务维护
- 语义缓存: 模型输入的语义级别缓存 (向量化), 直接存答案

#### Prompt Cache

- 重复前缀可直接复用 KV-Cache
    - 上下文只增不改有利于复用缓存
- 可显式创建
- 自动创建是根据长度递进的

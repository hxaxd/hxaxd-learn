# Retrieval(检索)

- 检索系统既要界定自己与记忆的边界, 也要覆盖数据进入, 表示, 查询, 存储和评测的完整链路, 因此按这些阶段和专用数据类型展开

## 边界

- 检索常与记忆和上下文注入混用, 先划清职责才能避免重复存储和错误归因

### Memory 与 Retrieval(记忆与检索)

- 记忆决定什么值得长期保存, 检索只决定当前任务如何取回信息, 两者寿命和责任不同

### RAG(检索增强生成)

- RAG 把检索结果送入生成过程, 它是检索的使用方式而不是检索系统的全部

- RAG
    - 狭义上指文本切割 -> 向量化 -> VectorDB -> 对提问向量化 -> 相似度匹配 -> 重排序 -> 注入上下文

## Pipeline(流水线)

- 检索质量由从原始数据到最终上下文的整条链共同决定, 不能只优化向量查询

### Ingestion(数据摄取)

- 查询效果首先受语料如何进入索引影响, 错误切分和元数据缺失无法在查询时完全补救

#### Parse(解析)

- 原始文件首先要转成可定位内容, 解析错误会污染所有后续阶段

#### Chunk(文本块)

- 索引单位决定语义完整性和定位粒度, 过大或过小都会降低检索质量

#### Metadata(元数据)

- 正文相似度无法表达来源, 权限和时间, 元数据承担这些结构化约束

#### Update(更新)

- 数据变化若不能增量同步, 检索会长期返回过时或已删除内容

### Recall(召回)

- 召回先决定候选信息是否有机会被看见, 是后续排序的上限

### Rerank(重排序)

- 高召回通常带来噪声, 重排负责在较小候选集中恢复精度

### Context Assembly(上下文组装)

- 排序靠前的信息仍要受窗口, 来源和结构约束, 组装决定模型最终看到什么

## Representation(表示)

- 同一内容可按语义, 词项, 关系或代码结构表示, 表示方式决定可回答的问题

- 结构取决于输入的信息类型与检索方式
    - 代码会使用 AST 进行结构化, 变成知识图谱
    - 图像会使用标签进行结构化, 变成标签列表
    - 文本可以按 chunk 进行结构化, 向量化后存入 VectorDB
    - 不管哪种, 都可以直接总结成文本

### Dense(稠密表示)

- 语义相近但措辞不同的内容需要稠密表示, 这是词项匹配无法覆盖的信号

### Sparse(稀疏表示)

- 专有名词, 编号和精确词项需要稀疏表示, 语义向量可能把它们过度平滑

#### BM25(概率相关性检索算法)

- 稀疏检索需要一个成熟基线说明词频, 文档频率和长度归一化如何共同排序

### Graph(图)

- 关系和多跳路径本身包含信息, 不能压缩成彼此独立的文本块

- 知识图谱
    - 编译知识大于检索知识
    - 不一定是用向量检索节点, 也可能是 LLM Wiki

### Code(代码)

- 代码检索依赖符号和控制结构, 自然语言表示不足以保持这些约束

## VectorDB(向量数据库)

- 稠密表示需要专门系统完成近邻查询和规模化维护, 其工程问题不同于检索策略

### Distance(距离)

- 向量只有通过距离函数才产生相似度顺序, 不同度量会改变召回语义

### Index(索引)

- 精确遍历无法支撑大规模低延迟查询, 索引负责在速度和召回率间取舍

#### Flat(扁平索引)

- 精确遍历提供召回率上限和小规模基线, 用于衡量近似索引损失

#### IVF(倒排文件索引)

- 先按聚类缩小搜索空间适合大规模查询, 但会引入分桶边界损失

#### HNSW(分层可导航小世界图)

- 图导航以较高内存换取低延迟和高召回, 代表另一类核心取舍

#### PQ(乘积量化)

- 向量压缩能显著降低内存和带宽, 代价是距离估计误差

### Filter(过滤)

- 语义相似并不保证租户, 时间和权限正确, 结构化过滤必须参与查询

### Update(更新)

- 知识持续变化, 索引的新鲜度和删除语义会直接影响事实正确性

### Distribution(分布式处理)

- 单机容量和吞吐存在上限, 分片与副本又会引入一致性和路由问题

## Strategy(策略)

- 基础召回不足以表达复杂意图和组合多路信号, 查询层还需要独立策略

### Query Rewrite(查询改写)

- 用户问题未必适合直接检索, 改写用于补全实体, 消除歧义和匹配索引语言

### Hybrid(混合检索)

- 语义与词项信号各有盲区, 混合检索用互补信号提高稳健性

### Fusion(融合)

- 多路召回产生不可直接比较的分数和排名, 融合负责形成统一候选序列

### Multi-Hop(多跳检索)

- 答案依赖多个相互关联事实时, 一次查询无法提前表达后续依赖

## Graph Retrieval(图检索)

- 关系密集问题依赖实体间路径而非单点相似度, 因而形成专门的图检索分支

### LightRAG(轻量图检索增强生成)

- 需要一个完整方案展示实体抽取, 图构建和局部全局查询如何组合

- 构建
    - llm-based 提取 chunk 中实体与关系为 K-V 形式 (实体名 - 实体摘要 / 实体暗示的全局主题 - 关系内容)
    - 对所有实体 / 关系的 K-V Embedding, 存入 VectorDB, 构建为知识图谱
    - 投入新文档不需要重新构建
- 检索
    - llm-based 提取 Prompt 中实体与抽象
    - 实体向量检索实体, 再根据图谱关系做二跳检索
    - 抽象向量检索关系, 获取相关实体

### graphify(图谱构建工具)

- 不同图构建工具采用不同抽取和存储取舍, 产品实例用于保留实现差异

- 不用向量化, 直接 LLM-based 抽取实体和关系, 构建知识图谱

## Code Retrieval(代码检索)

- 代码的符号, 调用和结构关系无法由普通文本切块完整表达

### AST(抽象语法树)

- 抽象语法树保留语法层级和符号边界, 是代码结构检索的基础表示

- AST
    - 对代码的最佳分析方式
    - 使用 Tree-sitter

### Semble(代码检索工具)

- 声明式代码检索展示模型如何用高层意图替代大量手工搜索

- 对代码进行 RAG, 提供一个声明式的代码检索工具
- 模型仅需要声明式地描述需要检索什么代码
- 自称相较于 grep+read 节省 98% 的 Token

### CodeGraph(代码知识图谱)

- 跨文件调用和影响分析依赖代码知识图谱, 单纯语法树无法覆盖

- 把代码建立为知识图谱, 包括符号关系, 调用图和代码结构
- 支持自动同步, 识别部分 WEB 框架的隐式调用关系
- 存在 SOLite, 支持全文搜索
- 支持影响分析, 避免 Agent 漏修改

## Evaluation(评测)

- 没有分阶段指标就无法判断问题来自召回, 排序, 上下文组装还是系统成本

### Recall(召回)

- 相关信息未进入候选集后续无法补救, 召回率衡量检索覆盖上限

### Precision(精确率)

- 候选噪声会占用上下文并干扰生成, 精确率衡量有效信息密度

### Relevance(相关性)

- 统计匹配不等于对当前问题有帮助, 相关性需要面向查询语义判断

### Groundedness(事实支撑度)

- 生成结果可能没有真正使用检索证据, 事实支撑度连接检索与最终回答

### Latency(延迟)

- 检索位于每次认知循环中, 延迟会直接累积到交互和长任务时间

### Cost(成本)

- 解析, 向量化, 重排和模型判断都会消耗资源, 质量提升必须与成本共同比较

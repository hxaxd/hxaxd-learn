# 多智能体

- 多智能体增加的不是单体能力本身, 而是组织形式, 连接拓扑, 协作, 通信, 共享状态, 调度和隔离等系统问题

## 边界

- 多智能体带来的协调成本很高, 必须先判断是否真的超过单智能体能力
- 任务正交 / 可并行

## 形态

### Subagent

- 子智能体由主智能体控制且上下文隔离, 适合有明确输入输出的局部任务
- 只能主从交流, 本质是声明式的工具调用
- 本质是一种压缩方式

### Team(团队)

- 成员长期保持身份并相互通信时, 才需要团队级任务和生命周期
- 有主从, 但是从智能体之间也可以有交互 (读写对方邮箱文件), 以协同完成任务
- 也可以使用黑板认领任务 (异步读取同一个黑板)
- 问题高度正交时有效
- 每个成员都需要有生命周期
    - Leader 管理 team config
    - 关机必须经过: 请求 -> 拒绝 / 同意并首尾 -> 确认关机 -> 通知团队并更新 team config
    - 所有消息传递与工作调度都依赖邮箱 + 轮询实现

## 拓扑

- 参与者相同也可能因连接结构不同产生完全不同的信息流和故障传播

### 顺序

- 后一步依赖前一步结果时, 顺序拓扑能保持因果关系并压缩上下文

### 并行

- 独立子问题可并行降低时间并增加视角, 但需要结果合并

- 增强鲁棒性, 但需要解决冲突
- 可从多角度探索问题

### 层级

- 大任务需要集中分解和监督时, 层级结构明确责任和汇报路径

### 对等

- 没有稳定主控者的协作需要成员平等协商, 其收敛和冲突机制不同

### 对抗

### 黑板

- 任务难以预先分配时, 共享黑板允许成员依据当前状态异步认领工作

### Dynamic Graph(动态图)

- 依赖关系可能在执行中才出现, 动态图允许拓扑随任务状态变化

## 通信

- 多个独立上下文无法共享隐含状态, 必须定义消息和共享数据的传递语义

### Message(消息)

- 直接消息是最小通信单位, 需要保留发送者, 接收者和因果关系

### Mailbox(邮箱)

- 异步成员不能依赖同时在线, 邮箱为消息提供缓冲和持久化

### Shared State(共享状态)

- 频繁共同读写的数据若全靠消息复制会失去一致性, 因而需要共享载体

### A2A(智能体间协议)

- 跨实现智能体协作需要统一发现, 任务和消息契约, 不能依赖内部工具调用

## 状态

- 协作过程产生上下文, 记忆和产物, 其所有权与来源比单智能体更复杂

### Context(上下文)

- 每个成员只应看到完成角色所需的信息, 上下文隔离控制成本和污染

### Memory(记忆)

- 跨任务经验可能属于个人或团队, 写入者和可见范围必须明确

### Artifact(产物)

- 代码, 报告和中间结果是成员交接的稳定载体, 不能只存在于消息中

### Provenance(来源追踪)

- 多人修改同一结论时必须知道来源和责任, 否则无法审查或回退

- 多智能体的记忆必须支持记录写入者

## 调度

- 多个成员会并发, 等待和失败, 因而需要高于单任务循环的生命周期控制

### Lifecycle(生命周期)

- 成员需要被创建, 空闲, 关闭和回收, 其寿命不应无限绑定团队

### Concurrency(并发)

- 并行成员会争用模型配额和环境资源, 需要团队级并发上限

### Synchronization(同步)

- 存在依赖的任务必须等待必要前置结果, 但又要避免全局阻塞

### Failure(失败)

- 单个成员失败不应默认拖垮整个团队, 需要重派, 降级或终止策略

## 隔离

- 并行成员若共享身份和工作区会相互破坏, 必须明确资源边界

### Identity(身份)

- 操作必须能归因到具体成员, 才能实施权限和审计

### Permission(权限)

- 不同角色不应继承主智能体全部能力, 最小权限降低协作风险

### Workspace(工作区)

- 共享文件会产生覆盖和脏状态, 工作区边界决定成员能否安全并行

### Worktree(工作树)

- 代码任务可用独立工作树隔离分支和目录, 同时保留低成本合并路径

- 通过 git worktree 的能力, 同时多目录开发多分支

## Evaluation(评测)

- 团队成功不能说明每个成员的贡献和额外成本是否值得

### Team Outcome(团队结果)

- 多智能体首先要证明整体结果优于更简单基线, 而不是只展示活动量

### Credit Assignment(贡献分配)

- 团队成功后仍要判断哪些成员和步骤真正贡献价值, 才能优化结构

### Cost 与 Latency(成本与延迟)

- 增加成员通常提高调用成本且未必降低关键路径时间, 收益必须与开销一起衡量

# 数据工程与大数据

## 参考资料

- Codex

## 总览

数据工程真正关心的不是一些抽象名词, 而是一段数据从产生到被使用的路径:

- 数据从哪里来
- 如何被采集进系统
- 进入系统后先放在哪里
- 如何从原始数据变成可分析, 可训练, 可服务的数据
- 最后被谁消费

所谓数据架构, 本质上就是这条路径的组织方式. 架构选择决定生命周期:

- 传统数仓: 先清洗, 再入仓, 以报表和经营分析为目标
- 数据湖: 先把原始数据存下来, 用的时候再解释和加工
- 流式架构: 事件一发生就进入日志, 下游持续消费
- 湖仓: 用对象存储保存数据, 用表格式和计算引擎提供类似数据库表的可靠性

如果只是了解数据工程, 抓住一条主线就够了: 数据源 -> 采集接入 -> 存储 -> 转换建模 -> 服务消费.

## 数据来源

### 业务数据库

业务数据库是最重要的数据源, 例如用户表, 订单表, 商品表, 支付表.

它们的问题是: 这些表首先服务在线业务, 不应该被分析任务直接拖慢. 所以一般不会让数据分析程序直接扫线上库, 而是通过备份, 主从库, CDC 或数据同步工具把数据复制出来.

早期做法是定时导出:

```sql
select *
from orders
where updated_at >= '2026-07-01';
```

这很直观, 但很容易漏数据或重复数据:

- 如果按 `created_at` 抽取, 更新过的旧订单会被漏掉
- 如果按 `updated_at` 抽取, 同一行可能被多次抽到
- 如果任务失败重跑, 必须保证重复写入不会造成脏数据

后来的做法是 CDC (Change Data Capture), 也就是监听数据库变更日志. MySQL 可以读 binlog, PostgreSQL 可以读 WAL, 将插入, 更新, 删除转换成事件流. Debezium 就是典型工具, 它把数据库变更持续推送到 Kafka 等消息系统.

### 行为事件

行为事件来自应用埋点, 例如曝光, 点击, 搜索, 收藏, 加购, 播放, 停留时长.

这类数据通常不是数据库表, 而是应用主动上报的事件:

```json
{
  "event_id": "01J0KX...",
  "event_type": "item_click",
  "user_id": 42,
  "item_id": 10086,
  "ts": "2026-07-02T10:20:30Z",
  "context": {
    "page": "home",
    "position": 3
  }
}
```

行为事件的特点是量大, 顺序重要, 迟到正常, 重复也正常. 采集系统通常需要:

- 生成全局唯一的 `event_id`
- 带上事件发生时间 `event_time`
- 尽量让事件可重放
- 允许下游按用户, 商品或会话分区处理

### 文件和外部数据

文件数据包括 CSV, JSON, Excel, 图片, 日志文件, 压缩包. 外部数据包括第三方 API, 广告平台数据, CRM 数据, 支付渠道对账数据.

这类数据的难点不是高并发, 而是不稳定:

- 字段名会变
- 文件格式会变
- 时间粒度不一致
- 对方接口可能限流或延迟

所以现代 ELT 工具常见做法是用 connector 接入, 先复制到数据仓库或数据湖, 再在内部做清洗.

### 机器和系统日志

机器日志包括 Web 访问日志, 服务日志, 监控指标, trace, IoT 设备数据.

早期常用 Flume 收集大量日志到 HDFS. 现在更常见的是日志代理 + Kafka / Pulsar / 云消息队列 + 对象存储或实时 OLAP.

日志类数据很适合追加写:

- 写入后基本不改
- 按时间分区
- 查询通常按时间窗口过滤

## 采集与接入

采集层的目标不是把数据变干净, 而是尽量完整, 可重放, 可追踪地把数据带进来.

### 早期: 文件导入和批量同步

最朴素的做法是每天跑脚本:

```bash
mysqldump app orders > orders.sql
hdfs dfs -put access.log /logs/2026-07-02/
```

Hadoop 时代, Sqoop 用于在关系型数据库和 Hadoop 之间批量传输数据, Flume 用于收集和聚合大量日志.

这种模式适合离线报表, 但不适合低延迟:

- 今天的数据明天才能用
- 出错后需要重跑整个分区
- 业务变化快时, 调度依赖会越来越乱

### 中期: 消息队列和日志总线

Kafka 的关键思想是把数据写入一个可持久化, 可重放的事件日志.

生产者把事件写入 topic, 消费者按自己的进度读取:

```python
from kafka import KafkaProducer
import json

producer = KafkaProducer(
    bootstrap_servers="localhost:9092",
    value_serializer=lambda v: json.dumps(v).encode("utf-8"),
)

producer.send("user-events", {
    "event_id": "e1",
    "event_type": "item_click",
    "user_id": 42,
    "item_id": 10086,
    "event_time": "2026-07-02T10:20:30Z",
})
```

Kafka 的价值不是简单替代队列, 而是让同一份事件可以被多个下游复用:

- 实时统计消费点击流
- 离线湖仓保存原始事件
- 推荐系统更新用户特征
- 风控系统识别异常行为

### 现在: CDC + Connector + 流批一体

现代数据接入通常由几类方式组成:

- 数据库变更: Debezium / Kafka Connect / 云数据库 CDC
- SaaS 数据: Fivetran / Airbyte 等 connector
- 行为事件: SDK / Collector / Kafka
- 文件数据: 对象存储事件通知 + 批处理任务
- 流式处理: Flink / Spark Structured Streaming

一个常见做法是所有数据先进入一个统一入口:

- 实时事件进入 Kafka
- 原始数据落到对象存储
- CDC 也转换成事件流
- 下游再按需要做离线或实时计算

这样做的好处是数据可重放. 如果某个清洗逻辑写错了, 可以从原始 topic 或原始表重新计算.

## 架构哲学

### ETL 数仓

ETL 是 Extract, Transform, Load. 先抽取, 再转换清洗, 最后加载到数据仓库.

这代表传统数仓思想:

- 入仓前就把数据规整好
- 数据模型比较稳定
- 面向 BI 报表和经营分析
- 常使用维度建模, 星型模型, 宽表

优点是查询体验好, 业务口径统一. 缺点是前期建模成本高, 原始数据保留不足时很难回溯.

### ELT 与云数仓

ELT 是 Extract, Load, Transform. 先把数据加载到仓库或湖里, 再用仓库算力转换.

云数仓和 dbt 让这种模式流行起来:

- 原始数据先进入 warehouse / lake
- 清洗和建模用 SQL 表达
- 模型之间形成 DAG
- 转换逻辑可以版本管理, 测试和文档化

一个 dbt 风格的模型大概长这样:

```sql
select
    user_id,
    count(*) as click_count_7d,
    max(event_time) as last_click_time
from {{ ref('stg_user_events') }}
where event_type = 'item_click'
  and event_time >= current_date - interval '7 day'
group by user_id
```

这类工具的本质是把 SQL 工程化, 而不是发明新的计算模型.

### 数据湖

数据湖的思想是先保存原始数据, 后续需要什么再加工什么.

典型形态是:

- 原始 JSON / CSV / 日志写入对象存储或 HDFS
- 清洗后转成 Parquet / ORC
- 按日期, 业务线, 表名分区
- 用 Spark / Hive / Trino 等引擎查询

数据湖的优势是便宜, 灵活, 能保存大量原始数据. 缺点是如果没有表格式和元数据管理, 很容易变成一堆互相不知道语义的文件.

### Lambda 架构

Lambda 架构把系统分成两条链路:

- 批处理层: 对全量历史数据做准确计算
- 速度层: 对最新事件做低延迟近似计算

例如推荐系统里:

- 批处理每天训练模型和刷新全量特征
- 流处理实时更新用户最近点击, 最近兴趣, 短时热度

缺点也很明显: 同一个业务逻辑可能要写两遍, 一遍 Spark, 一遍 Flink.

### Kappa 架构

Kappa 架构试图只保留流式链路. 数据都进入可重放日志, 需要重算时从日志开头重新消费.

它适合事件流本来就是事实来源的系统, 例如埋点, 监控, 风控. 但如果数据来自复杂数据库表, 或者历史数据规模太大, 完全靠流重放也不轻松.

### 湖仓

湖仓的核心是: 用对象存储保存数据文件, 用表格式管理事务, schema, 分区, 快照和历史版本.

常见表格式:

- Iceberg: 强调开放表格式, schema 演进, 分区演进, 多引擎访问
- Delta Lake: 强调 ACID, 元数据, 流批统一, 和 Spark / Databricks 生态结合紧密
- Hudi: 强调 upsert, 增量处理和近实时数据湖

湖仓解决的是数据湖的文件混乱问题. 过去一个表可能只是一堆 Parquet 文件, 现在表格式会记录:

- 当前表由哪些文件组成
- 每次提交新增或删除了哪些文件
- schema 如何演进
- 查询某个历史版本应该读哪些文件

## 存储

### 原始层

原始层保存最接近数据源的数据. 它不追求好查, 追求完整和可重放.

常见命名是 bronze / raw:

```text
s3://lake/bronze/events/dt=2026-07-02/hour=10/part-000.json
s3://lake/bronze/mysql/orders/dt=2026-07-02/part-000.parquet
```

原始层最好不要覆盖写. 如果上游重发, 用新的批次或版本记录下来, 后续清洗层再去重.

### 清洗层

清洗层把原始数据变成结构稳定的数据:

- 统一时间字段
- 统一主键
- 解析嵌套 JSON
- 去掉明显错误的数据
- 做幂等去重

常见命名是 silver / dwd / cleaned.

```python
from pyspark.sql import functions as F

events = spark.read.json("s3://lake/bronze/events/dt=2026-07-02/")

cleaned = (
    events
    .dropDuplicates(["event_id"])
    .withColumn("event_time", F.to_timestamp("ts"))
    .select("event_id", "event_type", "user_id", "item_id", "event_time")
)

cleaned.write.mode("overwrite").partitionBy("event_type").parquet(
    "s3://lake/silver/events/dt=2026-07-02/"
)
```

### 建模层

建模层面向业务问题组织数据:

- 用户宽表
- 商品宽表
- 订单事实表
- 日活指标表
- 推荐训练样本表

常见命名是 gold / dws / mart.

这里的数据不一定最通用, 但应该最适合消费方使用.

### 实时存储

不是所有消费都适合查湖仓.

低延迟场景通常会把数据写入专门的服务存储:

- Redis: 在线特征, 会话状态, 热 key
- Elasticsearch / OpenSearch: 文本搜索和日志检索
- ClickHouse / Pinot / Druid: 实时 OLAP 和用户可见分析
- Milvus / FAISS / 向量数据库: 向量召回和相似度搜索
- Feature Store: 管理离线和在线特征的一致性

这些系统不是替代湖仓, 而是为了服务查询模式.

## 转换与建模

### 从 MapReduce 到 Spark

MapReduce 的模型很朴素:

- Map 阶段把数据拆开并产生中间键值
- Shuffle 按 key 分组
- Reduce 阶段聚合

它适合大规模批处理, 但写起来笨重, 中间结果大量落盘, 迭代计算很痛苦.

Spark 把大数据处理变得更像写普通程序:

- DataFrame / SQL 表达结构化计算
- 内存计算改善迭代任务
- 一个引擎支持批处理, SQL, 流处理, 机器学习等工作负载

```python
from pyspark.sql import functions as F

daily = (
    spark.read.parquet("s3://lake/silver/events/")
    .where("event_type = 'item_click'")
    .groupBy(F.to_date("event_time").alias("dt"), "item_id")
    .agg(F.count("*").alias("clicks"))
)
```

### 从批处理到流处理

批处理处理的是有界数据: 昨天的日志, 上个月的订单.

流处理处理的是无界数据: 点击流一直来, 交易一直来.

流处理必须处理几个额外问题:

- 事件时间: 数据真实发生的时间
- 处理时间: 系统看到数据的时间
- 乱序: 后发生的数据可能先到
- 迟到: 几分钟前甚至几小时前的数据现在才到
- 状态: 统计窗口, session, 去重集合都需要保存中间状态

Flink 的强项就是有状态流处理. 例如统计每个商品 5 分钟点击数:

```sql
select
    item_id,
    window_start,
    window_end,
    count(*) as clicks
from table(
    tumble(table user_events, descriptor(event_time), interval '5' minute)
)
where event_type = 'item_click'
group by item_id, window_start, window_end;
```

### 维度建模

维度建模不是过时的报表技巧, 而是一种把业务问题变简单的方法.

基本对象:

- 事实表: 发生了什么, 如订单, 点击, 支付
- 维度表: 从哪些角度看事实, 如用户, 商品, 地区, 时间

订单事实表可能长这样:

```text
order_id | user_id | item_id | pay_amount | pay_time
```

商品维度表可能长这样:

```text
item_id | category | brand | price_band
```

分析时把事实和维度连接起来:

```sql
select
    i.category,
    count(*) as order_count,
    sum(o.pay_amount) as gmv
from fact_order o
join dim_item i on o.item_id = i.item_id
where o.pay_time >= current_date - interval '7 day'
group by i.category;
```

### 特征建模

机器学习场景里, 建模层还会变成特征层.

推荐系统常见特征:

- 用户最近 7 天点击次数
- 用户最近点击类目
- 商品最近 1 小时点击率
- 用户和商品类目的匹配度
- 用户 embedding
- 商品 embedding

离线训练需要历史特征, 在线推理需要最新特征. 如果两边计算逻辑不一致, 模型训练时看到的数据和线上服务时看到的数据不同, 效果会不稳定.

Feature Store 的意义就在这里: 管理特征定义, 离线特征和在线特征, 尽量减少训练和服务之间的不一致.

## 服务与消费

### BI 和报表

BI 消费的是稳定指标:

- 日活
- GMV
- 留存
- 转化率
- 点击率

这种场景更适合数据仓库, 湖仓金层, ClickHouse 等 OLAP 系统. 重点是口径一致, 查询稳定, 权限清楚.

### 实时看板

实时看板要求数据新鲜, 例如运营活动的实时曝光, 点击, 成交.

典型路径:

```text
App -> Kafka -> Flink -> ClickHouse / Pinot -> Dashboard
```

实时看板要接受一个事实: 新鲜度越高, 对一致性, 乱序处理和成本的要求越高.

### 在线服务

在线服务要求低延迟, 通常不能直接查离线湖仓.

例如推荐接口:

- 从 Redis / Feature Store 取用户实时特征
- 从向量库取候选商品
- 从在线模型服务打分排序
- 返回推荐列表

这种链路里, 数据工程负责把离线和实时数据准备成服务能用的形态.

### 训练与实验

机器学习训练需要可回放的历史数据.

好的训练数据集应该能回答:

- 样本来自哪些原始表
- label 是如何定义的
- 特征在当时那个时间点是否已经可见
- 这次训练能不能复现

这里最容易犯的错误是数据穿越: 使用了预测时不可能知道的未来信息.

## 调度只是胶水

Airflow, Dagster, Prefect 这类工具解决的是依赖和调度问题, 不是数据问题本身.

一个 DAG 可能长这样:

```text
extract_orders -> clean_orders -> build_user_features -> train_model -> publish_model
```

调度系统需要知道:

- 哪些任务依赖哪些任务
- 什么时候跑
- 失败后如何重试
- 任务日志在哪里看
- 哪个分区已经成功

不要把调度系统当业务逻辑的家. 业务逻辑应该在 SQL, Spark, Flink 或应用代码里, 调度系统只负责把它们串起来.

## 技术栈演进

### 第一阶段: 数据仓库

典型技术:

- Oracle / Teradata / SQL Server
- Informatica 等 ETL 工具
- 星型模型和报表系统

核心思想是先设计模型, 再接入数据. 适合业务稳定, 报表口径明确的公司.

### 第二阶段: Hadoop

典型技术:

- HDFS
- MapReduce
- Hive
- Sqoop
- Flume

核心思想是用廉价机器存储和处理海量数据. 这一阶段解决了数据量问题, 但开发体验差, 延迟高.

### 第三阶段: Spark + Kafka

典型技术:

- Kafka
- Spark
- Spark SQL
- Flink
- Hive Metastore

核心思想是把批处理和流式接入都工程化. Kafka 负责事件总线, Spark 负责大规模计算, Flink 负责更强的实时状态计算.

### 第四阶段: 云数仓与湖仓

典型技术:

- Snowflake / BigQuery / Redshift
- S3 / ADLS / GCS
- Parquet
- Iceberg / Delta Lake / Hudi
- dbt
- Airflow / Dagster / Prefect

核心思想是存储和计算分离. 数据放在云对象存储或云数仓里, 计算按需扩展. SQL 重新成为主要的数据建模语言.

### 第五阶段: 实时分析与 AI 数据栈

截至 2026-07, 新的数据系统明显向几个方向发展:

- 更实时: Kafka / Flink / Pinot / ClickHouse 让事件更快变成可查数据
- 更开放: Iceberg / Delta / Hudi 让湖上的表不再只是散乱文件
- 更面向机器学习: Feature Store 管理训练和推理特征
- 更面向向量检索: Milvus / FAISS / pgvector 等系统支持 embedding 相似度搜索
- 更自动化: connector 和 ELT 平台减少手写接入脚本

但底层问题没有变: 数据从哪里来, 是否可信, 能否重算, 能否服务当前查询.

## 推荐系统的一条完整数据生命周期

假设做一个电商推荐系统.

### 架构

```text
App / Web
  -> 埋点 Collector
  -> Kafka
  -> Flink 实时特征
  -> Redis / Feature Store
  -> 推荐服务

业务数据库 MySQL
  -> Debezium CDC
  -> Kafka
  -> Lakehouse Bronze
  -> Spark / dbt 清洗建模
  -> Lakehouse Silver / Gold
  -> 训练样本
  -> 模型训练
  -> 模型服务 / 向量库

Kafka / Lakehouse
  -> ClickHouse / Pinot
  -> 实时与离线看板
```

### 数据产生

用户打开首页, 系统曝光 20 个商品. App 上报 `item_exposure` 事件.

用户点击其中一个商品, App 上报 `item_click` 事件.

用户下单后, 订单服务写 MySQL `orders` 表. Debezium 监听 binlog, 把订单插入转换成事件.

这时有两类数据:

- 行为事件: 曝光, 点击, 停留
- 业务事实: 订单, 支付, 退款

### 实时链路

点击事件进入 Kafka 后, Flink 做几件事:

- 去重: 根据 `event_id` 去掉重复上报
- 补全: 根据商品维表补充类目和价格
- 窗口统计: 计算商品 5 分钟点击量和点击率
- 更新用户短期兴趣: 用户最近点击的类目和商品

这些结果写入 Redis 或 Feature Store, 推荐服务下一次请求时就能使用.

例如用户连续点击了几双跑鞋, 实时特征会很快反映出这个短期兴趣.

### 离线链路

同一份点击事件也会落到湖仓原始层.

夜间 Spark / dbt 任务会构造训练样本:

- 样本: 某次曝光中的用户和商品
- label: 曝光后是否点击, 是否加购, 是否购买
- 用户特征: 历史点击类目, 购买能力, 活跃度
- 商品特征: 类目, 价格, 近 7 天点击率
- 交叉特征: 用户最近兴趣和商品类目是否匹配

模型训练完成后, 产出:

- 排序模型
- 用户 embedding
- 商品 embedding
- 热门候选集

商品 embedding 写入向量库, 排序模型发布到模型服务.

### 在线推荐

用户再次打开首页:

- 推荐服务读取用户实时特征
- 从向量库或召回服务取候选商品
- 从 Feature Store 读取用户和商品特征
- 排序模型打分
- 返回推荐列表
- 曝光事件再次写回 Kafka

这就形成闭环:

```text
推荐 -> 曝光 -> 点击 / 购买 -> 数据 -> 特征 -> 模型 -> 推荐
```

### 一条点击事件的一生

一条 `item_click` 事件会经历:

- App 生成事件, 带上 `event_id`, `user_id`, `item_id`, `event_time`
- Collector 接收事件, 写入 Kafka
- Flink 读取事件, 去重并更新实时特征
- 原始事件落入 Lakehouse Bronze
- 清洗任务生成 Silver 事件表
- 建模任务生成用户行为宽表和训练样本
- 模型训练使用它作为正样本或兴趣证据
- 实时 OLAP 用它更新点击率看板
- 推荐服务间接使用它影响下一次推荐

这就是数据工程的核心: 一段数据不是静态表里的某一行, 而是在系统里不断改变形态, 从事实变成指标, 从指标变成特征, 从特征影响产品行为.

## 最后

了解数据工程时, 不需要一开始就陷进治理, 血缘, 元数据和质量平台. 这些东西重要, 但不是主线.

先抓住几个问题:

- 数据源是什么
- 数据是批量进入还是实时进入
- 原始数据能不能保留和重放
- 存储层是仓库, 湖, 还是湖仓
- 转换逻辑在哪里写, SQL / Spark / Flink / Python
- 消费方要的是报表, 实时看板, 在线服务, 还是模型训练

能把这些问题说清楚, 基本就能看懂一套数据系统为什么长成现在这样.

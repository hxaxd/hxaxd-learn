# 引言示例

## 总体骨架

```tex
\section{Introduction}
% 任务和应用
% 已有方法路线一以及局限
% 已有方法路线二以及局限和技术原因
% 本文解决的技术问题
% 核心认知和方法
% 技术贡献和优势
% 实验概述
% 贡献列表
```

## 任务和应用

### 版本一: 小众任务先定义任务

```text
[Task] aims to recover / reconstruct / estimate [output] from [input]
It supports applications including [application 1], [application 2], and [application 3]
```

写作顺序:

1. 用一句话说明输入和输出
2. 说明任务目标或范围
3. 选择两到三个代表性应用

### 版本二: 熟悉任务直接介绍应用

```text
[Task] is important for [application 1], [application 2], and [application 3]
```

任务已经为目标读者熟悉时, 不必重复教科书式定义

### 版本三: 一般任务 -> 特定设置

```text
[General task] is important for [applications]
This work focuses on [specific setting], where [input] is used to produce [output]
```

适用于具体问题设置较新, 但上层任务较熟悉的情况

### 版本四: 第一段直接暴露问题

```text
[Task and application importance]
Existing methods usually [common mechanism]
However, they fail under [condition] because [technical reason]
```

只有在第一段能够简洁说明问题时使用, 不要为了提前出现方法而压缩必要背景

## 引出技术问题

目标不是完整回顾领域历史, 而是让读者理解本文为什么必须解决这个问题

### 版本一: 已有任务和多代方法

```tex
% 任务面临的一般问题
% 传统方法怎样处理以及它的局限
% 较新方法一怎样处理以及技术原因
% 较新方法二试图解决什么, 仍然留下什么问题
% 明确本文解决的问题
```

逻辑链:

```text
一般困难 -> 传统方法 -> 新方法试图修复旧问题 -> 新方法留下目标问题
```

每次讨论局限时都回答:

- 哪类方法存在该局限
- 在什么条件下出现
- 表面现象是什么
- 本质技术原因是什么

### 版本二: 核心认知在传统方法中有先例

```tex
% 主流方法的共同做法和局限
% 传统路线中与本文核心认知相似的思想
% 传统路线为什么仍然不够
% 新方法为什么仍未解决目标问题
% 过渡到本文方法
```

该写法可以为核心认知提供历史依据, 但仍需要明确本文的技术差异

### 版本三: 新任务没有直接已有方法

```text
Our goal is to [goal]
This problem is challenging for three reasons
First, [challenge and reason]
Second, [challenge and reason]
Finally, [challenge and reason]
```

每个困难点应当相对独立, 并能够对应后文的一项方法设计或实验验证

## 介绍本文方法

写这一部分前回答:

- 方法解决哪一个技术问题
- 核心贡献是什么
- 方法本质上为什么能够工作
- 相对于已有方法有什么优势

### 版本一: 一项核心贡献和多项优势

```tex
% 提出方法或表示
% 指向封面图或技术流程图
% 一句话说明核心创新
% 说明核心实现
% 说明相对于已有方法的优势一
% 说明优势二
```

### 版本二: 两项相互衔接的贡献

```tex
% 提出总体框架和核心创新
% 介绍贡献一及其优势
% 指出贡献一之后仍然存在的问题
% 介绍贡献二如何解决该问题
% 总结两项贡献共同带来的能力
```

第二项贡献不应显得像临时补丁, 它需要由明确的问题自然引出

### 版本三: 在已有流程上增加新模块

```tex
% 说明采用的已有流程
% 说明新增模块是核心创新
% 给出驱动模块设计的观察
% 说明模块机制
% 与通用替代方案比较并解释优势
```

### 版本四: 观察驱动的方法

```tex
% 先说明关键创新
% 给出直观观察
% 根据观察推导具体设计
% 说明技术优势和可验证结果
```

## 不推荐的写法

### 从简单方案逐步打补丁

问题:

- 容易把工作呈现为可预见的增量修改
- 读者会因为作者已经铺好思路而低估真正的推理难度
- 每个模块看似只是修复上一个模块

改法:

- 从真实技术问题和本质原因开始
- 先给出统一的核心认知
- 说明各模块怎样共同实现该认知

### 只讲抽象认知而隐藏方法

问题:

- 读者无法判断贡献是否真实
- 新名词很多但机制不清楚
- 容易产生为了显得新颖而故意模糊的印象

改法:

- 在引言中讲清核心贡献具体怎样工作
- 把公式, 网络细节和实现参数留给方法章节

## 贡献列表

贡献列表中的每一项都应包含:

- 提出了什么
- 解决什么问题
- 带来什么技术优势或新知识
- 哪项实验支持它

不要把同一项贡献拆成多个近义句, 也不要把普通工程细节包装成独立贡献

## 自检

- 第一段是否让读者知道论文在解决什么
- 已有方法是否围绕目标技术问题展开
- 每项局限是否包含技术原因
- 方法是否准确回应前文问题
- 是否讲清方法为什么工作
- 贡献是否与方法和实验一一对应
- 是否存在实验无法支持的强主张

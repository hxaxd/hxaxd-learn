    人月神话

    • 编程系统产品就是原有工作量的九倍
      • 编程系统 (程序 + 接口) 是原有工作量的三倍
      • 编程产品 (程序 + 文档 + 测试) 是原有工作量的三倍
    • 人月是一个神话
      • 一个人员数量与项目进度可以互换的错觉
      • 向进度落后的项目中增加人手, 只会使进度更加落后
    • 哈伦米尔斯组织
      • 一个人负责设计与实现所有事情
      • 其他人只参谋或协助一个模块
      • 极大地减少了沟通开销
    • MVP 大概率会被完全推翻
    • 少数几个人构思一切并形成形式化的书面的文档
    • 统一团队的工具

    领域驱动设计 (DDD)

    • 领域模型
      • 面向特定业务目的, 抽象业务概念、关系、行为与规则
      • 同一现实对象可有不同模型
    • 模型驱动
      • 核心代码直接表达模型中的概念、行为与规则
      • 业务理解、模型、语言与代码共同演进
    • 战略设计: 划分模型边界, 明确各部分的协作关系
    • 战术设计: 在模型边界内组织对象、业务规则与操作

    战略设计

    • 领域愿景: 明确软件服务的业务目标、关键能力与独特价值, 作为模型取舍的依据
    • 子域: 按业务活动划分领域, 如销售、配送与结算
      • 核心域: 承载业务的独特价值, 集中投入建模与开发资源
      • 支撑域: 满足业务特有的辅助需求
      • 通用域: 承载普遍需求, 可采用成熟方案
      • 分类取决于业务定位, 如身份认证在商城中可属于通用域, 在身份服务公司中可属于核心域
      • 根据业务价值、规则复杂度与变化频率选择建模深度
    • 统一语言: 团队共同使用的业务概念、行为与规则, 在同一上下文内保持一致, 贯穿讨论、文档与代码
    • 限界上下文: 一套软件模型和术语的适用边界
      • 子域描述业务划分, 限界上下文描述模型划分, 二者的对应关系随系统演进调整
      • 边界内保持业务含义一致, 明确模型的维护责任; 部署方式按系统需求选择
    • 上下文映射: 描述现有模型边界及其关系, 明确依赖方向、权威业务事实的来源、变更责任与模型转换
      • 合作关系: 双方协调计划与变更, 共同保证集成结果
      • 共享内核: 多个上下文共同认可并维护的一小部分模型及代码, 变更需要相关团队协商
        • 共享包组织代码复用, 共享内核约定共同的业务含义与维护责任
      • 客户与供应商: 下游提出需求, 上游在计划与交付中承担相应承诺
      • 遵奉者: 下游采用上游模型, 接受其业务含义与演进约束
      • 防腐层: 将外部模型的业务含义翻译为本地模型, 如将外部支付状态解释为本地付款结果
      • 开放主机服务: 通过统一、稳定的访问协议向多个上下文提供能力
      • 发布语言: 以公开约定的信息表达形式与业务含义支持模型间交流
      • 各行其道: 在集成收益较低时, 各上下文独立实现所需能力
      • 大泥球: 含义与职责混乱的现有系统区域, 通过明确集成边界限制其影响
    • 模型提炼: 突出核心概念与规则, 将支撑能力、通用能力和复杂辅助机制组织到清晰的职责中
    • 整体结构: 以少量共同约定组织大系统, 随模型理解调整结构, 保留局部设计空间
      • 系统隐喻: 用共同理解的类比解释系统整体, 持续检验类比的适用范围
      • 职责层次: 根据业务职责、概念依赖与变化来源组织模型
      • 知识层: 将决定其他对象如何行为的规则本身建模, 明确规则与运行对象的关系
      • 能力组合: 通过稳定的业务抽象组织可替换、可组合的能力

    战术设计

    • 业务规则: 明确操作的前提、允许的变化与必须成立的结果, 按业务含义确定职责归属
      • 业务不变量: 每次有效操作完成后必须成立的约束, 如订单项数量必须为正
      • 业务策略: 表达可变化的业务决策, 如折扣、授信与定价规则
      • 业务生命周期: 明确对象的合法状态、状态转换与完成条件, 如取消订单后的退款义务
      • 时间含义: 区分当前信息与历史约定, 如商品维护当前售价, 订单保存成交价格与约定的配送地址
    • 领域对象: 用对象的身份、取值、行为与协作表达模型
      • 实体: 通过业务身份持续追踪同一对象, 通过业务行为维护自身状态与约束, 如订单
      • 值对象: 通过属性值表达含义, 相同取值的对象可互换, 通常不可变, 如金额由数值与币种共同确定
        • 选择依据业务用途, 如配送地址可作为值对象, 地址登记系统中的地址可作为实体
      • 聚合: 将一次业务变更中必须共同保持一致的对象划为一组, 如订单与订单项
        • 聚合根: 聚合对外操作的入口, 维护整个聚合的业务约束
        • 边界由业务不变量决定, 对象之间的关联可跨越聚合边界
        • 跨聚合流程明确允许的中间状态、完成时限与失败处理, 如退款处理中与退款完成
      • 领域服务: 表达超出单个实体或值对象自然职责的业务操作, 按业务规则协调领域对象
        • 服务承担业务职责, 一致性要求由聚合边界与流程约定表达并由实现保障
      • 模块: 将紧密相关的领域概念组织在一起, 以业务含义命名, 明确模块间的依赖
      • 工厂: 封装复杂对象或聚合的创建, 使创建结果满足必要约束
      • 仓储: 以业务对象集合的方式提供聚合的查找与保存, 通常按聚合根建立
        • 接口表达领域所需的存取能力, 具体实现负责存储访问与领域对象转换
      • 领域事件: 记录业务中已经发生的事实, 如订单已支付
        • 关注有业务意义的事实, 通常保持不可变, 可作为其他业务操作的响应依据
    • 模型质量: 概念含义一致, 规则归属明确, 相关概念能够局部理解, 变化能够集中到负责的部分
      • 意图明确: 操作名称与约定表达业务目的、前提和结果
      • 行为清晰: 区分计算与状态变更, 明确操作的影响范围
      • 表达简洁: 使用连贯的概念与可组合的操作, 借助适合业务的成熟形式表达规则
    • 分层实现: 按业务表达、用例组织、外部交互与技术支持划分职责, 使领域模型能够独立理解和验证
      • 领域层: 表达一个限界上下文内的业务状态、行为与规则
      • 应用层: 将领域能力组织成完整用例, 协调对象加载、领域操作、结果保存与事务
        • 命令: 表达希望执行的操作, 如支付订单, 执行时由领域模型检查业务规则
      • 基础设施层: 提供数据库、消息、外部服务等技术能力, 实现领域层或应用层所需接口
        • 替换实现时保持接口的行为约定, 包括事务与一致性要求
      • 接口层: 通过控制器将外部请求映射为应用用例, 处理路由、参数解析与响应转换
        • 同一应用用例可由 Web 接口、命令行、定时任务或消息处理器调用
      • 程序启动与生命周期: 选择并装配具体实现, 管理服务启动、关闭与资源释放
    • 取消订单的调用流程
      • 应用服务通过订单仓储取出订单聚合
      • 调用订单的取消行为, 由订单检查业务规则并更新状态
      • 应用服务通过仓储保存订单, 协调事务完成
      • 控制器将操作结果转换为接口响应

    Agent 软件工程

    • 编码绝非难点, 进入研发流程才是关键
    • Agent 有进入研发流程的能力, 但缺乏对应工具
    • 研发上下文需要完整且确定
    • 这个过程也需要链路追踪
      • 效能层面
      • 质量层面
      • 价值层面
    • 数字员工聚合上下文
      • 人负责维护意图与策略的边界
    • Based-Agent Engineering Infrastructure
      • 思考从研发流程中任意一点切入, 应提供完整上下文与进一步研发流程
      • 沉淀与转化知识库 / 代码库 / 技能中心
      • 提供流程化的 MCP / CLI
      • 统一环境与依赖
      • 沙箱
      • 快速组合 Agent

    委托与个人使用

    • 围绕可验收结果委托, 目标 / 约束 / 完成证据先形成共同理解
    • 给出仓库 / 原始材料 / 决定入口 / 可运行环境, 让 Agent 自己调查事实
    • 辅助解释 / 局部实现 / 完整任务委托根据问题与验证条件选择
    • 新的结果取舍需要人决定, 既定问题的探索 / 实现 / 普通修复自主推进
    • 问题返回人之前先提供证据, 比较结果与建议
    • 保存阶段产物与未决事项, 下一次从工作状态接续

    五类决定

    • 工具链与仓库: 职责, 依赖, 开发 / 验证 / 交付入口
    • 业务行为: 前置状态 + 动作 + 结果, 用可执行例子表达
    • 业务策略: 并发 / 重复 / 部分失败时接受什么
    • 数据面: 含义 / 所有权 / 来源 / 流向 / 访问 / 生命周期
    • 基础设施策略: 一致性 / 缓存 / 消息 / 重试 / 扩缩容 / 恢复怎样兑现业务承诺
    • 实现与测试都由模型产生, 一致可能来自同一次误解
    • 验收预期变化是新的决定, 不随实现方便悄悄改动
    • 架构与实现方式会定义结果时先确定, 局部实现选择按既有边界处理

    研发流程

    • 需求调查 -> 明确决定与验证 -> 实现 / 测试 / 修复 -> 评审 -> 集成 -> 发布 -> 使用反馈
    • 从任意入口接手, 都能找到目标 / 当前版本 / 约束 / 证据 / 下一步依赖
    • 开发环境与依赖可重建, 工具以完整工作为入口
    • 成员共享必要承诺, 局部工作区隔离, 在明确位置合并
    • 任务拆分按依赖与验收, 并行数量要匹配集成与审阅能力
    • 评审看重要含义与工程取舍, 验证覆盖不足处保留必要人工检查
    • 合入 / 部署 / 功能开放可以分开, 各自的授权与完成条件明确
    • 缺陷回流为回归任务, 方法回流为项目知识与技能

    两种节奏

    • 实现与验证按反馈连续推进, 人的参与按新决定出现
    • 已回答的问题进入共享材料, 避免每个任务重新要求人恢复背景
    • 等人决定时保留现场, 不依赖该决定的工作可以继续
    • 增加 Agent 可能增加人工队列, 不能只看同时开工数量

    效果

    • 从委托到可接受交付的总时间, 拆出执行 / 验证 / 等待
    • 人的调查 / 决策 / 审阅 / 接续时间
    • 真正的新决定与重复出现的旧问题
    • 交付后返工 / 遗漏 / 故障与成本
    • 相同业务要求与验收强度下比较, 不用代码量或模型生成速度替代收益
